### 3.1 Darboğaz: sipariş numarası satırı (tenant başına seri) + havuz tükenmesi

160 it/s'de `pg_stat_activity` / `pg_blocking_pids` örneği:

- `bayios_app`'in 100 bağlantısının **93'ü `Lock:transactionid`** bekliyor (havuz dolu → salt okunur `browse` istekleri de
  bağlantı bekler; PostgreSQL CPU'su yalnız ≈ 2,3 çekirdek, bellek 754 MiB — CPU darboğazı yok).
- Engelleme grafiği: **65 oturum** `INSERT INTO orders.order_number_sequences … ON CONFLICT DO UPDATE` üzerinde, engelleyen
  ise `idle in transaction` durumundaki başka bir sipariş oluşturma transaction'ı.
- Kök neden: boşluksuz sipariş numarası (PRD ORD-14, `OrderService.NextNumberAsync`) tenant/önek/yıl başına **tek satırı**
  kilitler ve kilit, isteğin UnitOfWork transaction'ı **commit edilene kadar** (satır fiyatlama, satır/geçmiş insert'leri,
  yanıt) tutulur. Tek tenant'ta sipariş oluşturma seridir; ≈ 48 oluşturma/s (120 it/s × %40) üstünde konvoy oluşur ve
  bekleyen istekler havuz bağlantısı tuttuğu için **diğer tenant'ların istekleri de** bekler.
- Değerlendirme: Bir KOBİ bayisinin gerçek hacmi (günde yüzlerce sipariş) bu sınırın çok altında → **ürün açısından düşük
  risk**. Ancak genel API rate limit'i olmadığından (güvenlik denetimi **M-3**) tek bir hesap bu konvoyu kasıtlı tetikleyip
  paylaşılan havuzu tüketebilir (gürültülü komşu / DoS). Öneriler (Backend): numarayı transaction'ın **sonunda** ayırın
  (kilit süresi ms'ye iner); tenant başına eşzamanlı yazma sınırı; havuzu tenant başına paylaştırma ya da istek başına
  bağlantı bekleme zaman aşımı; M-3 rate limiter.

## 4. Eşzamanlılık soak'u — rezervasyon yarışı

`ITERATIONS=200 RACERS=8 bash tools/load/run.sh soak` → ardından `bash tools/load/stack.sh verify`.

Her iterasyon **yeni bir üründe**: (1) mal kabul ile S ∈ {1..5} adet; (2) K sipariş (1–2 adet; Σ talep > S) oluştur + gönder;
(3) **Yarış A:** K onayın hepsi aynı anda (`http.batch`); (4) **Yarış B:** onaylananların yarısı iptal (rezervasyon serbest)
**ve aynı anda** reddedilenler yeniden onay; (5) API'den kontrol: `on_hand = S`, `reserved = Σ şu an onaylı miktar`,
`reserved ≤ on_hand`. İhlal → `oversell_violations` (eşik 0).

| Koşu | İterasyon × yarışçı | Süre | Onay | Ret (yetersiz stok) | Fazla satış | Beklenmeyen | http p95 / p99 |
|---|---|---:|---:|---:|---:|---:|---|
| Soak 200 | 200 × 8 | 87 sn | 450 | 2.307 | **0** | **0** | 63,3 / 78,7 ms |
| Uzun soak | 1.000 × 12 | 9 dk 58 sn | 2.254 | 19.518 | **0** | **0** | 68,2 / 84,9 ms |
| CI profili | 25 × 8 | 11 sn | 56 | 291 | **0** | **0** | 60,3 / 70,1 ms |

Toplam **1.225 iterasyon / 13.800 yarışan onay**: fazla satış 0, beklenmeyen yanıt 0, check %100. (test-strategy §4 #7:
"100 tekrar koşusunda tutarlı" → 1.225 tekrar.)

**Defter doğrulaması (`tools/load/verify.sql`, süper kullanıcı, salt okunur):** her koşudan sonra çalıştırıldı; tümü
`OK`. Son çıktı (basamaklı mix + iki 160 it/s koşusu + soak 200 + uzun soak sonrası):

```
movements 10621 · balances 1963 · reservations 27527 (active 17177) · orders 32768 (approved 9115, cancelled 1692,
pending_approval 17632, shipped 4329)
I1 unknown type or wrong sign: 0          (giriş > 0, çıkış < 0 — defter işaretli miktar tutar)
I2 balance.on_hand <> ledger: 0           (bakiye = hareketlerin toplamı, tenant/varyant/depo/raf anahtarında)
I3 balance.reserved <> open reservations: 0
I4 oversold balances: 0                   (on_hand ≥ 0, reserved ≤ on_hand)
I5 inconsistent reservations: 0
OK: ledger = balances, reservations = reserved, no oversell
```
Kontrolün kendisi de sınandı: tek bir bakiye `on_hand + 1` yapılan (commit edilmeyen) transaction'da `I2 = 1` ve
`STOCK INVARIANT VIOLATED` ile başarısız oldu.

## 6. CI

**Kısa sürüm CI'a bağlandı:** `.github/workflows/load-short.yml`, iş adı `load short` (ci-gate otomatik toplar; yol
filtresi: `services/api/**`, `tools/load/**`, migration/initdb betikleri, workflow'un kendisi).

| Adım | Süre (yerel ölçüm) |
|---|---|
| `stack.sh up` (EF betikleri + Postgres + publish + API) | ≈ 1,5 dk yerelde (CI'da `ci-migrations` ile aynı iş ≈ 2–2,5 dk) |
| `run.sh ci`: soak 25 × 8 + mix 5 ve 10 it/s (20'şer sn) | **≈ 1,5 dk** (k6 test süresi 11 sn + 51 sn, artı tohumlama) |
| `stack.sh verify` | < 5 sn |

**İlk CI koşusu (PR #158, `ubuntu-latest`):** iş toplamı **2 dk 52 sn** (yığın kurulumu dahil). Soak 25 × 8: 64 onay, 285 ret,
fazla satış 0, beklenmeyen 0, http p95 60,6 / p99 163,2 ms. Mix: 5 it/s → 19,0 istek/s, p95 20,1 ms; 10 it/s → 38,0 istek/s,
p95 18,9 ms; hata %0. `verify`: beş değişmez 0, `OK`.

Neden güvenilir: kapılar **deterministik** — `oversell_violations == 0`, `race_unexpected == 0`, `unexpected_responses == 0`,
`http_req_failed == 0`, `checks == 1` ve `verify.sql`'in beş değişmezi. Gecikme **kapı değildir** (runner'a göre değişir), yalnızca iş
özetine yazılır. Yerelde 160 it/s'de bile HTTP hatası 0 idi; CI profili 10 it/s'yi geçmez. Uzun soak ve basamaklı mix CI'da
koşmaz (süre); yukarıdaki komutlarla yerelde koşulur.

## 7. Yeniden üretme

```bash
bash tools/load/stack.sh up                         # izole yığın (55642 / 5390 / 5391)
STEPS=5,10,20,40,80,120,160 STEP_SECONDS=60 bash tools/load/run.sh mix

```

Kilit teşhisi için yük sırasında: `docker exec bayios-load-postgres psql -U postgres -d bayios` ile
`pg_stat_activity` / `pg_blocking_pids`.
